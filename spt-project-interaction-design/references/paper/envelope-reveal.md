# 信封展开 · Envelope Reveal

## 适用场景

每日寄语、朋友留言、写给未来的信等不需要立即阅读的内容。不要为紧急通知、错误信息或关键业务说明增加拆信步骤。视觉上的封口不代表内容被加密、定时锁定或真的发出了邮件。

## 必要分层

分别构建信封背面、信纸、信封前袋和封口，不把四者烘焙成同一张不可拆分的图。

- 信封背面在后，承接整体轮廓。
- 信纸位于背面与前袋之间，文字使用真实可选择或可访问的内容。
- 前袋挡住尚未抽出的信纸；袋口以上的信纸可以露出。
- 封口以袋口边缘为转轴，关闭时盖住袋口，打开时翻到合理的后侧。

Web 实现要检查 transform、透视与裁切产生的实际层叠关系，不能只加一个很大的 z-index 就认为分层正确。不要在整个组件外加会剪掉已抽出信纸的固定裁切。

## 动作顺序

`收起 → 翻开封口 → 抽出信纸 → 停稳阅读 → 放回信纸 → 合上封口`。

1. 点击或键盘触发打开，先翻开封口；袋口有足够空间后信纸再开始移出，可以有少量时间重叠，但不能穿过仍然闭合的封口。
2. 信纸从袋内连续移动到阅读位置，下半部分在离开袋口前持续被前袋遮挡。不要让整张纸透明淡入或从信封正面穿出来。
3. 停稳后文字保持清晰，不持续摆动。长信提供阅读高度和滚动空间，不依赖放小字号把一切塞进固定纸片。
4. 关闭时先让信纸回到袋内，再合上封口；不让盖子穿过还没收回的纸。

打开过程中点击关闭、收回过程中点击打开，应从当前进度安全反向，仍保留“先给袋口让出空间”的约束。重复点击不复制信纸、不叠加计时器、不触发多次业务操作。

内容加载与打开动画分开处理。内容未返回时有明确加载或错误状态；重试不丢失已有内容。若项目有已读标记、草稿或解锁条件，使用现有业务规则，不以动画结束作为所有状态的通用写入条件。

## 可访问性与布局

用有明确名称的按钮打开和关闭，并提供展开状态。焦点不随装饰运动乱跳；如果内容确实以模态阅读器打开，再沿用项目的模态焦点管理，不把普通页面内信封强行做成模态框。

减少动态效果时直接切换到可阅读或已收起状态。手机窄屏和软键盘出现时，正文和关闭入口仍应可见、可操作。

## 验收

- 翻盖、抽纸、阅读、回纸、合盖的每一步前后遮挡都合理。
- 信纸移动时字形不缩放、不变形，停稳后能阅读完整内容。
- 快速连续开关、中途反向、离开页面均没有闪回、重复信纸或残留事件。
- 长文字、空内容、图片未加载和请求失败都能合理显示与重试。
- 键盘和触摸都能开关，减少动态效果时仍能读到同一份内容。
